# 架构与设计取舍

## 完整链路

```
┌──────────────┐  说话   ┌─────────────────┐
│   人          │ ──────▶ │ 小爱音箱          │
└──────────────┘         └────────┬────────┘
                                  │ 唤醒词 + 语义
                                  ▼
                         ┌─────────────────┐
                         │ 米家场景 / 训练   │  只能操作米家设备
                         └────────┬────────┘
                                  │ 改一个开关
                                  ▼
                    ┌──────────────────────────┐
                    │ 小米云（MIoT 设备属性）      │
                    └────────┬─────────────────┘
                             │ 每 2 秒 prop/get 批量拉取
                             ▼
            ┌────────────────────────────────────┐
            │ Home Assistant                     │
            │  └ custom_components/miot_signal    │
            │      发现属性变化 → 执行脚本          │
            └────────┬───────────────────────────┘
                     │ script.cat_litter_clean
                     ▼
            ┌────────────────────────────────────┐
            │ PetKit 集成 → 小佩云 → 猫砂盆         │
            └────────┬───────────────────────────┘
                     │ 2 秒后
                     ▼
              把信号开关恢复原状（下次还能再按一次）
```

## 为什么不用这些方案

### 巴法云（很多教程里的做法）

教程里的常见链路是：米家 → 巴法云 MQTT → HA webhook。

**放弃原因**：巴法云全站在某些网络环境下不可达。企业网络里连 DNS 都被污染，直接打不开。

### Cloudflare Worker 中转

想着用一个 Worker 把米家的 webhook 转发到本地 HA。

**放弃原因**：`workers.dev` 域名在同一网络下被解析到 `198.18.x.x`（黑洞地址），同样不可达。
自建域名又要备案 + 公网 IP，成本不成比例。

### HA 自带的 webhook

看起来最直接：米家场景里能配「发送通知」，理论上能打到 HA 的 webhook。

**放弃原因**：一是米家的「发送通知」只能发到米家 App，不能发 HTTP；
二是这台机器上 HA 的 webhook 触发器也不响应（见 pitfalls.md 第 1 条）。

### 小爱开放平台自定义技能

**放弃原因**：需要企业资质、备案域名、HTTPS 公网回调、人工审核。个人做不下来。
这也是唯一能真正「拿到你说了什么」的官方途径，可惜门槛在资质上。

### 直接用 PetKit 的本地 API

**放弃原因**：PetKit 设备不出本地开放接口，只有 App 走的私有云接口。
逆向了也只能自己维护，而且换个固件就废。

## 为什么是「轮询属性」而不是「订阅事件」

理论上小米云会通过 MQTT 推送属性变化（xiaomi_home 内部就在用）。但实测：

- 音箱的属性几乎不推送，`media_player` 实体永远停在旧值
- 摄像头的部分属性有推送，但延迟不稳定，偶尔漏

而 `prop/get` 主动拉取是**确定性的**：每 2 秒问一次，一定拿得到当前值。

代价是每 2 秒一次 HTTPS 请求（一次批量带上所有属性，不是每个属性一个请求），
对家庭网络和云端配额都没什么压力。

**所以选择：不用推送，用轮询。** 简单、可预测、好排查。

---

## 为什么动作写在组件里，不用 automation

这台机器上 HA 的自动化触发器完全不响应（state / event / webhook / time_pattern 都试过）。
组件本身是 Python 代码，属性一变直接 `await hass.services.async_call(...)`，
完全绕开触发器这一层。

副作用是：动作逻辑和组件耦合了，改动作要改 `miot_signal.yaml` 而不是写 YAML 自动化。
但换来的是「一定能跑」，值得。

如果你在 Docker / 树莓派上部署，可以试试自动化能不能正常工作，能的话把这部分挪回
`automation.yaml` 会更符合 HA 的习惯。

## 为什么每次都要「恢复」

信号位是**边沿触发**：`true → false` 才算一次。如果不恢复，第二次按下去状态没变，
就再也不会触发了。

所以每次执行完动作，都要把那个开关推回原位：

```yaml
delay: 2                    # 等动作执行完
restore_entity: switch.xxx  # 推回原位
restore_value: "on"
```

`delay` 不能太短：小佩的设备收到指令后需要一两秒才开始动作，
开关恢复太早会和云端指令打架。实测 2 秒够用，倒砂这种长动作给 3 秒。

`restore_value: old` 是另一种用法：不管原来是什么状态，恢复成变化前的值。
适合「开和关都算触发」（`trigger: any`）的场景，比如插座。

## 数据流的安全边界

- 组件的所有网络请求都走 **xiaomi_home 内部的云客户端**，不自己存 token
- PetKit 的登录态由 PetKit 集成管理，组件只调它的实体
- 仓库里没有任何真实设备 ID、账号、令牌
- 设备属性只读，除非配置里明确要求恢复
